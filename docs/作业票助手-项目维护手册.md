# 作业票助手 · 项目维护手册

> 基线版本 **v3.6**（versionCode 27）· 2026-11-10
> 这份文档是给"以后的自己"看的：项目怎么组织的、规则藏在哪个文件的哪一行、新文件进来后按什么步骤改、改完怎么验收。
> 规则库快照见同目录 `规则库-安全措施-v3.6.csv`（125 条）与 `规则库-易错点-v3.6.csv`（74 条）；以后改规则先比对这两张表。资料库里对应的两张表分别叫「规则库-安全措施」「规则库-易错点」（表名不再带版本号，版本记在「版本」列）。

---

## 1. 这个项目是什么

给现场办票人用的**离线可用**工具，把《特殊作业许可证填写标准》和集团通报里的高频问题，变成能随手查、能自动算清单的 App。

| 能力 | 说明 |
|---|---|
| 8 类作业票速查 | 动火 / 受限空间 / 高处 / 吊装 / 临时用电 / 动土 / 盲板抽堵 / 断路 |
| 填票向导 | 勾现场实际情形 + 同时涉及哪些票，自动算出哪些措施必须勾、哪些要现场核实、哪些本次不涉及 |
| 安全措施四分类 | 必须勾选 / 核查确认 / 本次涉及 / 未涉及，逐条带确认人与"勾选原因" |
| 易错点红线 | 74 条（分票 60 + 全局红线 14，其中 8 条否决项），两个维度看：等级（否决项 / 常见扣分）× 类型（**票面办理 50 / 现场落实 24**）。现场落实类单独成区——它不是办票填错，是要到现场纠正的问题 |
| AI 审票 | 可配置厂商 Key，发截图或描述让 AI 按同一套规则逐条核对（可选功能） |

**技术形态**：纯静态 SPA（原生 JS，无框架、无构建、无后端），安卓端是手写 WebView 壳 + 本机回环 HTTP 服务，资源全部打包进 APK。所有规则数据内置在 `assets/js/data.js`，断网可用。

## 3. 数据模型（加规则前必读）

### 3.1 票种对象 `PERMITS[i]`

| 字段 | 用途 |
|---|---|
| `id` | 内部标识（hot / confined / height / lift / elec / dig / blind / traffic），跨表联动全用它 |
| `short` | 简称，界面标签用（动火 / 受限空间 …） |
| `when` | "什么时候需要办"，概览页首屏 |
| `levels` | 分级 + 审批层级 |
| `fields` | 填写要点，每条含 `name / req / good / bad / tip` |
| `risks` | `{must:[必选项], cond:[条件项]}`，向导里自动拼风险辨识清单 |
| `measures` | 安全措施数组，见 3.2 |
| `approvals` | 签字链 |
| `errors` | 本票种易错点，含 `level(critical/major) / kind（"onsite" 表示现场落实，缺省即票面办理）/ title / detail / src` |
| `wizard` | 向导配置：`questions[]` + `related[]` |

### 3.2 措施条目 `measures[j]`

```js
{ no: 3,                                  // 票面序号，必须与纸质票一致
  text: '动火点周围及附近的孔洞、窨井…',   // 原文，尽量不改字
  must: true,                             // 无条件条目
  kind: 'verify',                         // 只在 must 里用：现场核实型
  why: '勾√ = 已沿动火点周围及下方 15m…',  // 勾选原因，界面显示在条目下方
  cond: '动火同时涉及高处作业时必选',      // 条件提示，核查确认/条件项用
  cross: ['height'],                      // 关联票联动；['*'] = 任一其他票
  note: '补充说明',                        // 可省略
  by: '属地监护人' }                       // 确认人，必填
```

### 3.3 四类状态怎么算（唯一权威规则）

判定顺序在 `app.js` 的 `evalMeasure()`，**按优先级从上到下，命中即返回**：

| 优先级 | 条件 | 结果 | 票面 |
|---|---|---|---|
| 1 | `m.must === true` | **必须勾选** | 打 √ |
| 2 | 用户手动点过这行（`bag.m[no]` 为 true/false） | 本次涉及 / 未涉及 | √ / 空 |
| 3 | `m.cross` 命中本次涉及的票 | **本次涉及** | 打 √ |
| 4 | 场景题 `add` 命中 | **本次涉及** | 打 √ |
| 5 | `m.cross` 存在但没命中 | **未涉及** | 空（可点一下改） |
| 6 | 其余 | **核查确认** | 留空 |

两条不能破的口径：

- **只有第 5 种能判"未涉及"**。原文带"如/如有/涉及…时"的条件项一律进"核查确认"留空，由人现场定，App 不下结论。
- **`must` 一律打 √**，包括 `kind:'verify'` 的现场核实型（核实结论是"没有"也照样打 √）。核实型必须写 `why`，界面用「勾选原因」标签显示；不写就等于让用户盲勾。

当前分布：125 条 = 必须勾选 54（其中核实型 17）· 核查确认 64 · 关联票条件 7。

### 3.4 交叉联动表 `CROSS`

```js
CROSS[关联票][主票] = { add:[关联票要加勾的措施号],
                        mainAdd:[主票要加勾的措施号],
                        risk:[关联票补的风险], mainRisk:[主票补的风险],
                        note:'现场提示' }
```

已有联动：动火↔高处/受限/临电、受限↔高处、动土→动火、盲板→动火、高处/临电/盲板/受限→任一其他票（`cross:['*']`）、**吊装↔断路（占道吊装）**。

向导里"同时涉及其他特殊作业"芯片、以及场景题带 `rel` 的（例：吊装"占道/需封路"→ `rel:'traffic'`），都会把关联票整张带进结果区。

## 4. 版本与发布（硬规则）

任何改动、哪怕只改一行文案，**必须**同步改四处，缺一处用户就会觉得"装了新版还是旧界面"：

| 位置 | 改什么 |
|---|---|
| `assets/js/data.js` 顶部 | `const APP_VERSION = 'x.y';`（首页底部、设置页底部显示，用户凭它确认包） |
| `android/build_apk.py` | `VERSION_CODE`（整数，每次 +1）、`VERSION_NAME`（x.y） |
| `sw.js` | `CACHE = 'permit-guard-vN'`（每次 +1，网页版防缓存） |
| 产物 | `android/build/permit-guard-x.y.apk` |

构建：

```bash
cd android && python build_apk.py
```

依赖：`C:/Android/Sdk`（build-tools 36.0.0、platforms/android-34）+ 系统 JDK。脚本自己找 aapt2 / d8 / zipalign / apksigner，不走 Gradle。签名用 `permit-guard.jks`（同一密钥，可直接覆盖安装，不用卸载）。

### 4.1 在线更新（v3.1 起）

两条通道，都在 `assets/js/update.js` + `UpdateManager.java` 里：

| 通道 | 改什么内容时用 | 用户看到 |
|---|---|---|
| **网页热更新** | 规则、文案、界面（99% 的情况） | 点一下，几秒完成，页面自动重载，不用装包 |
| **安装包升级** | 原生能力变化（权限、接口、新桥接方法） | 下载 190 KB，走系统安装界面，装完自动带最新网页 |

**仓库**：`q1753772789/permit-guard`（公开）。`main` 分支就是线上版本，App 直接读它。

**清单与产物**（全部放仓库的 `update/` 下，由 `tools/publish.py` 生成）：

```
update/latest.json                 版本清单（含 size / sha256 / 说明）
update/web/www-3.5.zip             网页包，index.html 在压缩包根目录
update/apk/permit-guard-3.5.apk    安装包
```

> `latest.json` 里 `web.path` / `apk.path` 是**仓库根相对路径**（带 `update/` 前缀）。
> 早期版本漏了这个前缀，App 拼出来的下载地址少一层目录、热更新必然 404。
> `update.js` 的 `urlOf()` 现在会兜底补前缀，但新清单一律写全。

`latest.json` 关键字段：`web.code`（`3.1`→`301`，前端按 major*100+minor 比）、`web.minApk`（低于这个 versionCode 的包不许热更新，防接口不兼容）、`apk.versionCode`。前端和后端**都按 code 比较，不按字符串比**。

**发布一条命令**（仓库地址已在代码里，不用每次带 `--repo`；**默认就会推到 GitHub**）：

```bash
python tools/publish.py --notes "本次改了什么"
# 只发网页（改了规则/文案，没重新打包 APK）：加 --web-only
# 只想生成产物不推送（调试用）：--no-push
# 首次接入或换仓库才需要：--repo 用户名/仓库名（会改 update.js 并自动重建 APK）
```

> 约定：**任何改动都要 `publish.py` 推一次**，否则手机上查不到更新。
> 推完会自动清掉 `update/` 里除「当前版 + 上一版」之外的旧包（`prune()`），避免仓库无限变大。


脚本会：打包网页 zip → 复制 APK → 算 sha256 → 写 `latest.json` →（可选）提交并上传。

**推送走 GitHub API，不是 `git push`**：本机访问 `github.com` 主站会超时，但 `api.github.com` 通。所以：

```bash
python tools/gh_setup.py --token ghp_xxx     # 首次：建仓库 + 上传全部文件（也可 --repo 指定名字）
```

token 放项目根 `.github_token`（已在 `.gitignore`），之后 `--push` 自动读，不用再带。权限：classic 勾 `repo`；fine-grained 需要 `Contents: Read and write` +（要自动建仓库时）`Administration: Read and write`。

**App 端取清单的四级顺序**（`update.js` 的 `bases()`）：

| 顺位 | 源 | 缓存特性 | 用途 |
|---|---|---|---|
| 1 | `raw.githubusercontent.com` | 源站/CDN 会缓存，发版后可能几分钟读到旧清单 | 首选，最快 |
| 2 | `api.github.com/repos/<repo>/contents/...` | **无缓存**，公开仓库可匿名读（60 次/小时/IP） | 纠错主力 |
| 3 | `cdn.jsdelivr.net/gh/<repo>@main` | 分支引用最长缓存 12 小时 | 前两个都不通时兜底 |
| 4 | `<owner>.github.io/<repo>` | 需另开 Pages，默认不通 | 备用 |

**关键机制：缓存复核**。CDN 会返回上一版清单，表现成"刚发版却查不到更新"。所以只要第 1 顺位这份清单**没发现任何更新**，程序会自动再用第 2 顺位（无缓存）核实一次；发现更新的正常情况不多发请求。实测：装 3.4 查更新，先打 raw 拿到旧清单，再打 api 确认 3.5，正确提示。

**原生取文本必须异步**（v3.6 起，`UpdateManager.java`）：

| 接口 | 行为 | 谁在用 |
|---|---|---|
| `httpGetStart(url)` | 起后台线程，**立刻**返回任务号 | 新网页 |
| `httpGetTake(token)` | 取结果：`{done:false}` 还在跑 / `{done:true,text}` 完成 | 新网页 |
| `httpGet(url)` | 同步阻塞，只作兼容 | 老网页包 |

`@JavascriptInterface` 的方法是在 **WebView 的 JS 线程**上同步执行的。原来的 `httpGet` 直接在里面做网络 IO，
四个源依次超时（8s 连接 + 20s 读取）时整页僵死、点哪都没反应、连"正在检查…"都画不出来——这就是 v3.5 里
「点检查更新 App 卡死」的原因。现在前端 `nativeGet()` 是"启动 + 每 120ms 轮询"，并带 20 秒总预算，
超时给明确提示（"网络太慢，检查超时"），`state.checking` 一定会复位。

**原生的 `httpGetBlocking` 必须带 `Cache-Control: no-cache`**。不带这个头，raw 返回的就是缓存里的旧清单——
这一点用 curl 实测过，带与不带结果不同。

**降级保护**：`evaluate()` 只认「远端 code > 本地 code」，清单比本地旧时一律不提示，避免用户被"更新"回退到旧版本。

**安全边界**（改代码时别拆）：
- 只接受 https，域名在 `UpdateManager.ALLOW_HOSTS` 白名单内；
- 每个包都校验 `sha256`，不符直接丢弃，绝不落盘；
- 解压先到 `<版本>.tmp`，确认有 `index.html` 才改名生效；解压时拦 `..` 路径；
- 热更新目录 `filesDir/web/<版本>/` 优先于 APK 内置资源，找不到的文件回落内置；
- 设置页「回退到内置版本」= 删掉 marker + 目录，页面重载即恢复。

**必须注意的三件事**：
1. **仓库只能公开**（私有仓库的文件要令牌，不能内置进 APK）。也就是说 `update/web/*.zip` 里的规则、`docs/规则库-*.csv` 全都能被任何人下载。若要保密，把 `update/` 放到公司内网静态服务，用 `--repo` 之外的方式改 `update.js` 的源，别用公开 GitHub。
2. **签名密钥 `android/permit-guard.jks` 绝不能进仓库**（已写进 `.gitignore`）。拿到它就能签出"看着像更新"的恶意包，用户会照装。
3. 热更新只动网页文件，**不碰** `NativeStore` 里的模型配置和对话记录。

## 5. 以后有新文件/新规则时，按这个流程走

用户会不定时发来：新修订的填写标准、集团通报、事故案例、现场退票记录。统一按下面六步处理，不要跳步。

**Step 1 · 落库与定位**
先把文件存进资料库并记下来源；再对照 `规则库-安全措施-v3.6.csv` / `规则库-易错点-v3.6.csv`（或资料库里同名两张表）找出"这条规则现在是怎么写的、在哪个票种第几条"，避免重复添加或两张口径打架。

**Step 2 · 判断改法**（同一份文件里往往几种都有）

| 文件里说的是 | 改哪里 |
|---|---|
| 新增一条票面措施 / 现措施文字要按新标准改 | `PERMITS[].measures` 增改条目 |
| "这条其实哪个场景都要做" | 加 `must:true`（核实类补 `kind:'verify'` + `why`） |
| "这条只在…时才有" | 加 `cond` 说明；若随另一张票才成立，加 `cross` |
| 通报里的典型违章 | `PERMITS[].errors` 或 `GLOBAL_ERRORS` 新增（写清 `src` 来源）。**先判类型**：`kind:'onsite'` 只给三类——①现场该做的措施没做（没铺接火毯、没摆灭火器、没加盲板、没倒空置换）②人员定位卡没戴 ③监控点位没对准作业面；其余（填错、漏签、勾错、该勾没勾）一律归"票面办理"，不加标记。**关键**：即使是"勾√前必须先到现场核实"的措施，只要纠正动作落在票上（重新勾、补备注），也属票面办理 |
| "现场同时涉及 X 票就要办 Y 票" | `CROSS` + 向导 `questions` 加带 `rel` 的场景题 + `related` 数组 |
| 风险辨识清单变了 | `PERMITS[].risks.must / cond` |

**Step 3 · 改 `data.js`**
只改数据，不改判定逻辑。新措施的 `by`（确认人）必填、`text` 尽量贴原文、序号沿用纸质票编号。

**Step 4 · 跑校验**（见第 6 节，全过才算完）

**Step 5 · 升版本 + 出包 + 说清差异**
给用户回话时讲明白：改了几条、哪几条从哪类挪到哪类、打勾数从几变几、为什么这么归。

**Step 6 · 更新快照**
重新生成 `docs/规则库-*.csv`（版本号跟着改），把这次改动写进 `.workbuddy/memory/` 当日日志与 `MEMORY.md` 的口径段。

## 6. 验收清单（改完必跑）

| # | 检查 | 合格线 |
|---|---|---|
| 1 | 逻辑自测（node 直接跑 `evalMeasure/wzCompute`） | 8 票种计数自洽，合计仍 125（或改动后的新总数），无 NaN |

## 9. 踩过的坑（别再犯）

1. **别用"未涉及"兜底条件项**。1.7 之前把"清洗吹扫合格"这类判成不涉及，被用户当场纠正。判"未涉及"只有一个合法来源：`cross` 存在但本次没办那张票。
2. **别整页重建**。AI 流式一次 60ms 重建整列 DOM + 重播 0.28s 入场动画 = 满屏闪；向导重绘不带 `keepScroll` = 每点一下跳回顶部。
3. **别把核实型留空**。"确认动作"类条目（十不吊、30m 内无排放）留空会被理解成"不用勾"，2.0 犯过，2.1 已改回必勾 + 勾选原因。
4. **重写函数别顺手删被引用的工具函数**。`byTag` 曾被误删，整页报错。
5. **版本号必须升**，四处同步；否则用户装了新包看不出变化。
6. **截图验证要禁动画**，否则 headless 拍到淡入中间态，看起来像布局崩了；360px 也别指望 headless 复现（最小视口 500），按几何数据判断是否溢出。
7. **改口径要同时改提示词**。`ai.js` 的 system prompt 与 `data.js` 的 `buildRuleDigest()` 都描述分类规则，漏改会让 AI 给出和界面相反的说法。
8. **别让外部 CDN 脚本待在 index.html 里**。同步 `<script src="https://cdn...">` 在 WebView 里拉不到就一直等，排在它后面的 4 个本地 js 全部推迟执行 → 白屏、启动卡。现场没网时最明显。2.4 删掉了一行 jsdelivr 的遗留引用。
9. **看着像重复或矛盾，先问一句"是不是两个人、两个数"**。别急着合并或"理顺"——票面很多栏目就是配套的：
   - 临电要点 3/4 都带 kW：一个是电工核定的**许可总容量**，一个是用电人填的**设备明细**，两个数要能对上（设备之和 ≤ 许可功率）。不是重复，但原文案没点破，办票人会读成重复——**区别必须写进文案**。
   - 临电要点 5/6 都提监护人：本票就是**两人监护**——属地监护人 + 现场作业监护人（由作业负责人担任）。第 5 项讲这两人、第 6 项说明作业负责人正是其中之一，既不重复也不冲突。2.4 曾误判成矛盾去改，2.5 已改回"两人监护，缺一不可"。同类参照：动火「属地监护人 + 现场作业监护人（可由作业负责人担任）」、断路明写「双重监护」。
10. **各票种的"安全交底人"范围不同，这是原文规定，不是我抄漏**（2026-11-08 用户确认）。动火/高处：副操、组长、技术员、副班长、班长；受限/动土/断路：多一个工段长；临电：必须是持电工证的作业负责人；吊装：必须是吊装指挥人员；盲板：只写"覆盖全部人员"。**不要为了版式整齐把各票统一成一个口径**——每张票按自己的标准填，改动前先对原文。
11. **"被通报了"不等于"票办错了"，但"要先到现场核实才敢勾"也不等于"现场落实"**（2026-11-08 用户纠正）。2.6 首版把 25 条判成现场落实，其中「不适用的措施一律打√或直接留空」判错了——它通篇讲的是**勾没勾、勾得对不对**，纠正动作是回票上重新勾、补备注；哪怕勾之前要求沿动火点下方 15m 走到位，仍属票面办理。**判定只看一件事：纠正动作落在哪儿**——改票/补签/补勾 → 票面；现场补做措施、补戴定位卡、重调监控点位 → 现场落实。当前 24 条（分票 20 + 通用 4），其余 50 条是票面办理。
    - **混合条目的判法**：一句话里既有票面动作又有现场动作时，按**通报里的实际情形 + 主要纠正动作**定。如「灭火器、水带勾"未涉及"或没摆到现场」归现场落实（用户确认）——通报实情多是灭火器锁在柜里没拿到现场，纠正动作是去现场摆出来；而「不适用的措施一律打√」归票面，因为它的纠正动作就是重勾+补备注，没有别的现场动作可做。
12. **"重开就没了"先查 origin，别怀疑 localStorage 坏了**（2026-11-08 用户报障：配好 AI 模型、也对话了，重开软件后设置和记录全不见）。安卓壳不是 `file://` 而是本机回环服务，`LocalServer.start()` 原来用 `new ServerSocket(0)` 拿随机端口；页面 origin 是 `http://127.0.0.1:端口`，**localStorage 按 origin 隔离**，端口一变就是另一个存储空间，旧数据还在但读不到。修法：端口固定优先（47821–47825，带 `SO_REUSEADDR`），并用 `NativeStore`（应用私有目录 `files/webstore/<key>`）做真源——JS 侧统一走 `Store.get/set/remove`，**不要直接调 localStorage**。注意：已丢失的旧数据在旧端口的 WebView leveldb 里，换端口后读不回来，用户需重填一次。
13. **我们办的是电子作业票，文案里不要出现"动笔/落笔/笔误"**（2026-11-08 用户指出）。首页横幅改成「先看红线，再填票」；「现场核实后自己落笔」统一改成「现场核实后自己勾选」/「在 App 里勾选」；动火引言的"最贵的一次笔误"改"失误"。**自查方法**：`grep -rn "动笔\|落笔\|笔误" assets/js/`，应为 0 命中。同理避免"打印/纸质/手写/涂改"这类只有纸票才成立的词。
14. **APK 的 versionCode 一直是 3，`--version-code` 根本没生效**（2026-11-10 做在线升级时发现）。`aapt2 link --version-code 22` 只在清单里**没写** versionCode 时才起作用；`AndroidManifest.xml` 里写着 `versionCode="3"`，就以 3 为准。后果：系统设置里所有版本都显示 1.2，靠版本号判断新旧永远失败。修法：`build_apk.py` 的 `stage_manifest()` 先把清单复制到 `build/` 并替换版本号，再拿副本去 link。**每次发版都要 `aapt2 dump badging xxx.apk | head -1` 核对一次**，别信构建日志里的"版本: x.y"。
15. **raw 会返回旧清单，别把它当"最新"**（2026-11-10）。`raw.githubusercontent.com` 的 `Cache-Control: max-age=300`，但实测发版 10 分钟后仍返回上一版；**带 `Cache-Control: no-cache` 请求头才能拿到最新**（curl 对照验证过）。所以原生 `httpGet` 必须加这个头，且客户端要在"没发现更新"时用 GitHub contents API 复核一次。jsDelivr 对 `@main` 缓存最长 12 小时，只能当兜底。
16. **清单里的 `path` 必须带 `update/` 前缀**。原来写的是 `web/www-x.zip`，而文件在仓库 `update/web/` 下，App 拼出 `/main/web/www-x.zip` 直接 404——清单能读到、包下不下来，最难查。`publish.py` 已改为写全路径，`update.js` 的 `urlOf()` 也会给老格式补前缀。
17. **GitHub 新建的 fine-grained token 页面没有 "Select scopes"**（2026-11-10）。那是 classic token 的字段；fine-grained 改成「Repository access + Permissions」两级，要传文件给 `Contents: Read and write`，要脚本建仓库再给 `Administration: Read and write`，`Metadata` 自动 Read-only 不用动。
18. **别在 `@JavascriptInterface` 方法里做网络 IO**（2026-11-10，v3.5 的卡死事故）。WebView 调用 Java 桥是**同步**的，Java 不返回，JS 线程就一直停着——渲染、点击、动画全部冻结。v3.5 的 `httpGet` 就是这么写的，四个更新源挨个超时，用户点一下"检查更新"整页僵死几十秒以上且毫无提示，只能杀进程重开。凡是可能超过 100ms 的操作（网络、文件、解压）都得做成「启动 + 轮询」两步。自查信号：用户说"点了一下就没反应了/整个 app 卡死了/转圈都没有"，先怀疑同步桥。
